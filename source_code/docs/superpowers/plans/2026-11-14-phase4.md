# Phase 4 implementation plan

> For agentic workers: use superpowers:subagent-driven-development for isolated implementation tasks and review.

Goal: implement the supplied Phase 4 specification within the existing application without resetting data.

Architecture: signed SePay attempts and verified IPN/tra cứu SePay share a single atomic settlement service. Lock order first, then payment and ingredients in ID order. Deduct snapshot reservation quantities, persist immutable costs and movements, consume reservation, update order, enqueue durable email in one transaction. SMTP runs outside that transaction. Return only queries trusted state.

Tech stack: existing Java/Spring/PostgreSQL and React/TypeScript; Spring Mail.

- [ ] Payment module: configuration, HMAC codec, attempts, IPN, tra cứu SePay, ownership, review handling, migration V9.
- [ ] Email and fulfillment: durable outbox, bounded retries, escaped HTML, notifications API, PAID→PREPARING→COMPLETED. Migration V10.
- [ ] Frontend: payment controls/result polling, payment and notification management, staff transitions, preserve existing styling.
- [ ] Tests: signed notifications, malformed/duplicate/concurrent callbacks, rollback, late settlement, stock/cost snapshots, email failure, role and transition checks; regression on isolated PostgreSQL.
- [ ] Docs and environment examples: setup, endpoints, workflow, limits, real sandbox checklist.

Shared API contract (ApiResponse wrapper except raw SePay IPN): POST /payments/sepay/create {orderId} returns {checkoutUrl,fields,paymentAttemptId,transactionReference,expiresAt}; GET /orders/{id}/payment-status returns {orderId,orderStatus,paymentStatus,transactions:[PaymentView]}; GET /payments/reference/{reference} same owned status. PaymentView fields id,orderId,transactionReference,providerTransactionNo,amount,status,bankCode,paidAt,expiresAt,failureReason,createdAt. Admin GET /admin/payments and /review returns Page<PaymentView>; POST /admin/payments/{id}/query returns PaymentView. PATCH /(admin|employee)/orders/{id}/status {status} returns OrderResponse. Email API shape is coordinated with implementer.

Baseline: 65 backend tests passed and frontend build passed immediately before implementation. Review actual SRS alongside supplied prompt. No secrets in source; no database reset; no claim of live SePay completion without actual merchant test.
